# Cost Model

How GPU spend is calculated, attributed, and surfaced through the platform.

---

## GPU pricing reference

Hourly per-GPU prices are denormalised into `silver/jobs.price_per_gpu_hour` from a constant map in [spark/jobs/bronze_to_silver.py](../spark/jobs/bronze_to_silver.py):

| GPU type | $/GPU-hour | Tier |
|---|---:|---|
| H100-SXM5-80GB | 4.25 | flagship |
| A100-SXM4-80GB | 3.00 | performance |
| A100-PCIe-40GB | 2.21 | performance |
| A10G | 0.90 | standard |
| RTX-4090 | 0.74 | standard |

The same prices are also referenced by the synthetic generator in [data/generator/job_events.py](../data/generator/job_events.py) so that generated `cost_usd` values agree with the recalculated values in `int_job_costs`.

Tiers (`flagship`, `performance`, `standard`) are derived in [int_job_costs.sql](../dbt/models/intermediate/int_job_costs.sql):

```sql
CASE
  WHEN gpu_type LIKE 'H100%' THEN 'flagship'
  WHEN gpu_type LIKE 'A100%' THEN 'performance'
  ELSE 'standard'
END AS gpu_tier
```

| Model | $ / 1K tokens |
|---|---:|
| llama-3-405b-instruct | 0.0035 |
| stable-diffusion-xl | 0.0400 |

| llama-3-70b-instruct | 0.0009 |
| codellama-34b-instruct | 0.0008 |
| mixtral-8x7b-instruct | 0.0006 |
| llama-3-8b-instruct | 0.0002 |

Total request cost is `(input_tokens + output_tokens) / 1000 × cost_per_1k_tokens`. Errors (status_code ≠ 200) are billed at $0.

## Billing rules (job costs)

The intermediate model `int_job_costs` ([dbt/models/intermediate/int_job_costs.sql](../dbt/models/intermediate/int_job_costs.sql)) encodes four rules that turn raw job records into a billable `cost_usd`:

### Rule 1 — Successful jobs are billed for actual duration

```
cost_usd = duration_hours × gpu_count × price_per_gpu_hour
```

### Rule 2 — OOM kills (exit_code = 137) are billable

The customer's job consumed the GPU; they pay for what they used. `exit_code = 137` is treated identically to `exit_code = 0` for billing purposes.

### Rule 3 — Platform errors (exit_code = 143) are not billed

When the platform's job scheduler kills a pod (SIGTERM after a node drain, scheduler eviction, etc.) the customer is not charged. `cost_usd = 0` regardless of duration.

### Rule 4 — In-flight jobs accrue cost from `started_at` to now

When `ended_at IS NULL` (the job is still running, or its completion event has not arrived), cost accrues from the start time:

```sql
ROUND(
  (EXTRACT(EPOCH FROM (CURRENT_TIMESTAMP - started_at)) / 3600.0)
  × gpu_count × price_per_gpu_hour,
  6
)
```

This matters for two reasons:
1. Real-time dashboards show "spend so far" without waiting for the completion event.
2. The 15% of jobs that are late-arrival in the generator (or in production, jobs whose webhook is delayed by a transient outage) still get a cost on the day they ran.

When the late completion event arrives, the next batch run's MERGE updates `ended_at`, `duration_hours`, `cost_usd` to their final values. The accrued estimate gets corrected on the next pipeline run.

## Job status taxonomy

The same model derives a status label used everywhere downstream (cost dashboards, success rate calcs, SLA checks):

| `job_status` | Condition | Billable? |
|---|---|---|
| `running` | `ended_at IS NULL` | Yes (accrued) |
| `succeeded` | `exit_code = 0` | Yes |
| `oom_killed` | `exit_code = 137` | Yes |
| `platform_error` | `exit_code = 143` | No |
| `failed` | otherwise | Yes |

`oom_rate = oom_killed / total` is surfaced in `cost_attribution` and `/cost/orgs` — a useful signal for customer success ("this org keeps OOMing on 70B models on 40 GB cards").

## Attribution grain

`gold/cost_attribution` ([dbt/models/marts/cost_attribution.sql](../dbt/models/marts/cost_attribution.sql)) aggregates to:

```
(job_date, org_id, user_id, model_arch, gpu_tier, gpu_type, framework)
```

Why this grain:

- **`job_date` × `org_id`** — the minimum required for monthly invoicing.
- **`user_id`** — engineering leadership wants per-team chargeback within an org.
- **`model_arch`** — product wants to know which workloads are most expensive ("are 70B trainings disproportionate to 7B?").
- **`gpu_tier` + `gpu_type`** — capacity planning needs to know not just $ but also which hardware is in demand.
- **`framework`** — observability into whether DeepSpeed users have measurably different cost profiles.

A surrogate key `attribution_id = MD5(grain columns)` is generated by the [generate_surrogate_key macro](../dbt/macros/generate_surrogate_key.sql), making writes idempotent (re-running dbt produces the same key for the same grain).

## Aggregations exposed at this grain

| Column | Definition |
|---|---|
| `total_jobs` | `COUNT(*)` |
| `succeeded_jobs`, `oom_jobs`, `failed_jobs`, `running_jobs` | Filtered counts by `job_status` |
| `total_cost_usd` | `SUM(cost_usd)` |
| `total_gpu_hours` | `SUM(gpu_hours)` |
| `avg_cost_per_success_usd` | `AVG(cost_usd) FILTER (WHERE job_status = 'succeeded')` |
| `avg_duration_hours` | Successful jobs only — failed jobs skew the mean |
| `max_duration_hours` | Across all jobs |
| `oom_rate` | `oom_jobs / total_jobs` |
| `success_rate` | `succeeded_jobs / (total_jobs - running_jobs)` (excludes in-flight) |

## Aggregations the API exposes

`GET /cost/orgs` rolls up to the (date_range, org) grain — useful for monthly billing reviews. `GET /cost/models` rolls up to the (date_range, model_arch, gpu_tier) grain — useful for product analytics.

`GET /metrics/summary` returns:
- `total_cost_7d` — 7-day rolling spend across the entire fleet
- `total_gpu_hours_7d` — capacity consumed
- `avg_success_rate` and `avg_oom_rate` — coarse health signals

These are powered by the same `cost_attribution` table — there is no second cost model.

## Inference cost path

Inference cost flows separately. Each request's `cost_usd` is set at write time by the producer (`(total_tokens / 1000) × cost_per_1k_tokens`), persists into `silver/inference`, and aggregates into `gold/job_performance_sla.total_cost_usd` at the (date, model_id, region) grain.

`/sla/models` exposes per-model cost alongside latency so the on-call engineer responding to an SLO breach can immediately see whether the breach correlates with a usage spike.

---

## Drift detection

Two safeguards catch billing bugs before they reach production dashboards:

1. **Great Expectations** asserts `mean(cost_usd) ∈ [1.0, 500.0]` over the entire `silver/jobs` table. A unit-conversion bug (cost-per-second instead of cost-per-hour) would push the mean outside this range and fail the GX gate before Gold is touched.
2. **Custom dbt test** [`assert_positive_costs.sql`](../dbt/tests/assert_positive_costs.sql) fails if any row in `cost_attribution` has `total_cost_usd < 0`. A signed-arithmetic regression cannot ship.

## Scaling considerations

The current cost path is single-pass — `int_job_costs` reads all of `silver/jobs` every run. At ~50K jobs that takes seconds. At a real-cloud scale (millions of jobs per day) the model would need:

- Incremental materialisation (`{{ config(materialized='incremental', unique_key='job_id') }}`)
- Partitioning by `job_date` on the Gold table (Delta partition spec)
- A separate accrued-cost model that runs hourly for "running" jobs, leaving the daily model for finalised jobs

None of this changes the public columns of `cost_attribution` — only its build strategy.
